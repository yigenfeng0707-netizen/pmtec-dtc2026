PMTEC (Persistent Multi-domain Tactical Engagement Coordinator) 是面向 DTC 2026 数字孪生挑战赛 Level 3 的数字孪生战场系统。系统以 ASDA 认知循环（Act-Sense-Decide-Adapt）为核心运行范式，融合 LVC 三层架构（Live-Virtual-Constructive）实现真实/虚拟/构造数据的统一时空协调，通过 多层 AI 决策栈（UCB1 + Q-Learning + DQN + MADDPG）实现从自适应拦截到多智能体协同的全谱系智能决策，并以 Kalman 滤波 + JPDA 实现多源传感器航迹融合。

系统在 4 种对手策略（饱和攻击、隐身突防、电子战、诱饵群）下的 Monte Carlo 验证拦截率均 ≥70%，达到参赛目标。安全认证体系（JWT + RBAC + mTLS + 审计日志）、可观测性体系（Prometheus + Grafana 34 面板）和 CI/CD 流水线（Docker + GitHub Actions）构成准生产级运维基座。

3. DTB 模型与 gRPC 四服务

系统遵循数字孪生战场（DTB）模型规范，将战场能力拆解为四个 gRPC 服务，每个服务可独立部署、水平扩展，通过 gRPC Health Check Protocol 实现健康监控和故障转移。

WarEngine (Port 50051)

职责：PMTEC 仿真核心，驱动 LVC 时空协调、ASDA 循环执行、威胁生成与拦截评估。

核心接口：

  • GetState — 返回全量态势状态（实体、航迹、ASDA 阶段、网络脆弱性）
  • StreamEvents — 服务端流式推送实时事件
  • StartSimulation / StopSimulation — 仿真生命周期控制

BattleNetwork (Port 50052)

职责：gRPC 航迹分发与实体状态广播，维护分布式战场网络拓扑。

使用 networkx 构建战斗网络图，优化散射路径规划；支持 22 个军事基地的连通性分析。

ApplicationStore (Port 50053)

职责：能力模块管理—F-35 打击、IAMD 防御、ISR 情报收集等插件式能力注册与发现。

基于 dt_platform 包的 PluginManager 和 DTRegistry 实现。

PlugAndPlay (Port 50054)

职责：动态组件注册与服务发现，支持运行时插件加载/卸载。

REST Gateway (:8080) 提供 HTTP 策展层，降低前端集成门槛。

gRPC 高可用 (P1-a)

通过 _HAChannelManager 实现多后端故障转移：

  • 健康检查：gRPC Health Check Protocol，HealthServicer 为 4 个服务设置 SERVING 状态，set_unhealthy() 支持优雅下线
  • 故障转移：主节点 TRANSIENT_FAILURE 时自动切换到备份节点，支持配置多个 GRPC_HA_BACKUP_HOSTS
  • 指数退避重连：初始 1000ms，倍率 2.0，上限 30000ms，最多 5 次重试
  • 后台健康轮询：每 10s 一次 grpc_health.v1.HealthCheckRequest

4. ASDA 认知循环

ASDA（Act-Sense-Decide-Adapt）是 PMTEC 的核心运行范式，灵感来自军事 OODA 循环但针对数字孪生场景重新设计。每个循环周期 10 秒，Decide 阶段每 40 秒运行一次 DQN 推理。

6. 多层 AI 决策栈

PMTEC 采用四层 AI 决策栈，从快速反应到深度推理逐层递进，每一层解决不同时间尺度的决策问题。

第一层：UCB1 + Q-Learning（快速自适应，<1ms）

模块： learning/ucb1_intercept.py + learning/qlearning_dispersal.py

  • UCB1：多臂老虎机选择拦截策略（direct / predictive / saturation），基于置信上界平衡探索-利用
  • Q-Learning：离散状态-动作空间散射方案选择，Q 表覆盖基地状态×散射方案
  • 运行频率：每个 ASDA 周期，无需训练预热

第二层：DQN 深度强化学习（核心决策，<50ms）

模块： deep_rl/dqn_agent.py + deep_rl/pmtec_env.py

  • 算法：Stable-Baselines3 DQN，MLP 策略网络（182·256·256·6）
  • 观测空间：182 维浮点向量
    • 22 基地 × 5 特征（飞机归一化、损毁归一化、传感器存在、威胁接近度、电子干扰）= 110 维
    • 12 全局特征（总威胁数、总航迹、ASDA 周期、脆弱性、拦截率、散射率、EW 活跃数、网络攻击阶段、网络效能、天气探测因子、能见度、侧风）= 12 维
    • 10 威胁 × 6 特征（纬度、经度、类型编码、到达时间、航迹置信度、传感器覆盖）= 60 维
  • 动作空间：6 离散动作（3 拦截策略 × 2 散射方案）
  • 训练：200K 步 XPU 课程学习，Intel Arc GPU 加速，3 阶段递进难度
  • 奖励塑形：拦截成功(+10) + 基地存活(+1/tick) - 损伤(-5) - 时间惩罚(-0.01)

第三层：MADDPG 多智能体（协同决策，CTDE）

模块： deep_rl/maddpg_agent.py + deep_rl/multi_agent_env.py

  • 架构：Centralized Training Decentralized Execution（集中训练分散执行）
  • 双智能体：拦截智能体（3 动作）+ 散射智能体（2 动作）
  • Actor 网络：局部观测 → Gumbel-Softmax → 动作概率
  • Critic 网络：全观测 + 全动作 → Q 值（集中训练时可见所有智能体信息）
  • 与 IQL 的关键区别：IQL 的 Critic 只看自己的 (obs, action)；MADDPG 的 Critic 看到所有智能体的 (obs, actions)，训练更稳定
  • Target 网络：软更新 τ=0.005，共享经验回放缓冲区

第四层：传感器优化（元决策）

模块： learning/sensor_optimizer.py

基于感知效能矩阵优化传感器部署位置，最大化区域覆盖与威胁探测概率。在 Adapt 阶段触发，调整传感器阵列配置以适应当前威胁分布。

XPU 加速方案

系统运行在 Intel Arc Graphics (8.58GB) 环境，通过 PyTorch XPU 后端（torch 2.14.0+xpu）实现 GPU 加速训练和推理。编码优先级：QSV → NVENC → CPU（当前环境无 NVIDIA GPU，nvidia-smi 不可用）。

# XPU 设备检测
device = detect_best_device()  # 优先 "xpu", 回退 "cpu"
model = DQN("MlpPolicy", env, device=device, ...)

# SB3 XPU 模式下 predict 返回 ndarray
action, _ = model.predict(obs, deterministic=True)

7. 传感器融合与航迹管理

Kalman 滤波航迹（P3-2）

KalmanTrack 类实现常速度运动模型的状态估计，状态向量 [lat, lon, v_lat, v_lon]（位置+速度，单位为度）。支持多源传感器测量更新，协方差矩阵 4×4 初始化为速度高不确定度。

  • 状态转移矩阵 F：常速度模型，dt=1
  • 过程噪声 Q：适应机动目标，加速度噪声 σ_a=0.001°
  • 测量噪声 R：根据传感器源置信度动态调整
  • 航迹生命周期：最大老化 60s，最低置信度 0.3，融合间隔 5s

JPDA 多目标关联（P5-1）

联合概率数据关联（Joint Probabilistic Data Association）解决多目标场景下的测量-航迹关联模糊问题。对每个落入关联门限内的测量，计算所有可行关联假设的后验概率，按概率加权更新航迹状态。

实时数据接入（P1-b）

ADS-B 航迹

  • 真实 API: opensky-network.org/api/states/all
  • 超时 10s，重试 3 次，线性退避
  • 失败自动降级到模拟数据
  • 输出: 航班号、纬度、经度、高度、速度

天气数据

  • 真实 API: api.open-meteo.com/v1/forecast
  • 按基地位置逐个请求，失败跳过
  • 输出: 风速、风向、能见度、降水、云量
  • 影响: detection_range_factor、visibility_factor
